# Membership and verification

Members and staff are separate authority domains. Staff remain User records with Owner/Administrator/Editor/Author policies, passwords, first-Owner bootstrap and operator recovery. Member records have no staff role and cannot authenticate a staff session, edit content, upload media, administer settings, inspect drafts or change releases. Matching a staff email never links either identity. Owner staff grants remain their separately authenticated audited workflow.

Membership defaults disabled. Canonical modes are disabled, email, discord and both. A00 selected both to mean either independently verified method; the amendment's email_and_discord spelling is not accepted as an alias or mandatory dual-provider policy. Requested mode, provider readiness and explicit new-registration enablement are separate. Unready providers prevent enablement; an Owner can save a requested mode with registration closed. With email/Discord configured but registration closed, existing active Members can sign in; disabled closes both methods. Policy changes revoke Member sessions and pending proofs without touching staff sessions. Both does not silently downgrade a selected method: an available alternative is a separate explicit user choice.

Owner Accounts is under Settings at /admin/accounts, with direct manage_identity authorization and optimistic policy revision. Stale forms conflict rather than overwrite. No provider secret enters that form or Site, content export or logs. The actual provider adapter reads only a canonical absolute current-user-owned0600 JSON file specified by RAILPRESS_MEMBERSHIP_CONFIG. Missing/unsafe/unverified config is unavailable. A host verification flag is an operator attestation, not automatically tested live delivery. Synthetic adapters are explicitly code-injected subclasses used only in isolated qualification, never selected by a public setting, URL, import or permissive environment flag.

## Email proof

Email is UTF8-validated, trimmed, NFC/case-fold normalized and indexed by SHA256 to keep engine collation behavior equivalent. Invalid addresses fail safely. Requests are bounded per client, normalized address and site using private-HMAC keys and SecurityClock2 windows. New and existing addresses follow the same request/delivery path and generic public response; no account is created at request time. An SMTP error records a failed proof and cannot verify an account.

A signed purpose/audience-bound token is stored only as a digest. Email contains a fragment-only link and a separate manual token for no-JavaScript use. No token query is needed. The verification page removes the fragment from history, fills a core-owned form and requires explicit CSRF POST. A browser nonce also binds the proof to the browser that requested it, preventing login CSRF. Open links in that initiating browser. GET and mail scanners do not consume tokens. Proofs expire within15minutes under SecurityClock2 elapsed, absolute, epoch and boot-domain checks. Resend invalidates older outstanding proofs for that mailbox. Consumption is transactional and one-use under the Site aggregate lock.

Only successful provider acceptance plus accepted local proof establishes mailbox control. SMTP acceptance alone is not proof of delivery/readership; later bounces are not automatically processed by this implementation. Actual SMTP/inbox/bounce qualification and provider retention remain operational gates. Verification does not establish a legal identity.

## Discord proof and linking

A CSRF-protected local POST creates the pending request and renders a no-store, no-referrer core confirmation page. Only its explicit provider link leaves the site; no form redirect, automatic navigation or third-party request is required. The strict form-action self and script-src none policy stays intact. The page discloses the actual provider host and requested ID/email scope; a pending request is not verified membership.

Authorization uses a confidential code grant, mandatory state/browser binding, S256 PKCE, exact registered HTTPS callback, required pinned issuer and fixed server endpoints. Identity is the immutable provider subject. Ordinary sign-in requests only identify when email is not required; otherwise identify and email. An explicit account link requests identify and email because its separately disclosed matching-mailbox proof is required, even under an identify-only sign-in policy. Missing/unverified provider email is refused under email-required policy. Bot/system identities and malformed payloads are rejected. Provider username, guild/role flags and browser-supplied user claims never assign authority. No automatic merge by mailbox.

A Member can explicitly link Discord only with a current session, proof from the last5minutes, CSRF and confirmation, and a verified provider mailbox matching the Member mailbox. Another Member's identity and duplicate provider links cannot be stolen or replaced by racing requests. Mutable Discord names do not change identity. A changed required mailbox is refused rather than silently overwriting the local mailbox; use fresh local mailbox proof and reviewed account recovery. Disconnect requires a separately proved local mailbox and available email sign-in, then revokes old sessions. This avoids silently stranding a Discord-only account.

Access/refresh tokens are transient and never stored, logged, exported or refreshed in background. The transient grant is revoked after current-user lookup; failed exchange or revocation refuses completion. Exchange, user lookup and revocation share one five-second monotonic budget. If it is exhausted, no new revocation request starts; an unrevoked remote grant may remain until provider expiry or operator revocation, while local verification is refused. A provider denial, revocation or outage does not create a Member. Existing local Member sessions are bounded to1hour: external revocation is not instant local-session revocation. Local logout, account closure, disconnect and Owner policy changes revoke local access. A fresh provider sign-in is required for a new session; an immediate remote-deauthorization webhook is not claimed.

## Session, data and retention boundary

Member sessions have a separate opaque cookie-session key and database authority, rotate the browser session on acceptance and use SecurityClock2. Linking/email change/disconnect/closure require proof within5minutes. Mailbox changes require the same current initiating session plus fresh proof of the new mailbox, refuse collisions and revoke prior sessions/proofs. Account export returns only that Member's profile and linked provider subject, never secret/session/token/deadline material or other users. Closing membership revokes access and leaves a closed record; it is not automatic erasure. Re-enrollment using a closed record is refused pending operator review.

Challenge/state lifetime is15/5minutes; bounded cleanup removes expired challenge/state/session/throttle records using the deadline authority. Cleanup runs opportunistically before new challenges; operators should also run Membership.cleanup! regularly on quiet sites. Each call checks at most50old rows per class. Active proofs are retained; hard2000-row limits refuse new work instead of evicting fresh credentials. Closed Member/linked subject retention and any later purge must be explicitly documented by the site operator, with actual hosting/provider logs and backup obligations reviewed. No zero-personal-data or GDPR-exemption claim follows.

Core account pages are HTTPS-only, CSRF protected, no-store, noindex/nofollow, no-referrer, and independent of public themes. Ordinary home/content browsing does not create a membership flow or contact Discord/mail providers. Necessary authenticated security state is preserved; A06 broader anonymous privacy qualification is separate.

CMS content portability deliberately excludes membership policy, Member identities, provider readiness and all authentication material. These security-local settings require review at the destination and cannot activate registration through import. Own-Member account export is separate. Logical application schema12 adds membership tables/columns without rewriting old migration history or dropping staff/content data. Native promotion/revert from a schema11 predecessor remains separately unqualified; a same-version diagnostic install is not upgrade proof.

The host-owned file-backed secret store is permission-restricted (0600/current application user) and excluded from code/content archives. This implementation does not supply at-rest encryption, a managed secret vault or production credential custody; the operator must qualify host encryption/access/rotation before any live provider use. Public request responses do not distinguish new/existing Members or SMTP failure. This is not a constant-time network guarantee: provider and network latency vary.
