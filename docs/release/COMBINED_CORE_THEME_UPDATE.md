# Owner-approved combined update

`Update Railpress and Theme` creates one exact, idempotent Owner request. It binds the signed release digest/version, actor authentication epoch, active theme/overlay/revision and optional locally staged compatible theme/overlay. Existing theme identity/customization is preserved unless an explicitly selected newer package has a valid Owner preview. Changed authorization or appearance refuses execution; request UUID reuse for another operation/selection is rejected.

The web process never executes a shell, reads private signing keys or performs host operations. Its button is present only with fresh, verified native status attesting combined protocol v1, promotion capability, recovery drill and snapshot readiness. Current host admission remains **isolated-synthetic-nginx-v1**, production_qualified:false and independent_utc_qualified:false. Production, unknown profiles and ordinary installations are unsupported for activation; use the separately reviewed native operator procedure and obtain host/time/backup qualification first.

A separately provisioned operator uses `bin/railpress-combined-update ROOT publish|sweep|prepare UUID|process UUID`. Its private `combined-policy.json` requires format railpress.combined-policy.v1, exact deployment_id, owner_request_approval:true and external_time_adapter_ready:true. This is explicit operator provisioning, not self-admission by the application. No daemon, global service or real time authority is installed automatically.

Prepare verifies the exact GitHub inbox assets and creates existing staging/native challenges under ROOT/combined-admissions/UUID/challenges.json. The independently approved time adapter supplies stage-utc.json and promote-utc.json using their respective challenge bindings and unchanged deadlines. Process calls existing M11 staging then M12 approved promotion, verifies their signed receipts and post-core health, rechecks theme revision/Owner, optionally activates the selected immutable package/overlay via Themes::Manager, and checks final health. Deployment requires the operator to run sweep and publish fresh status; no application-owned scheduler is granted privilege.

A per-request nonblocking private filesystem lock prevents duplicate compositions. Terminal combined receipts are immutable and status-signed, bound to selection SHA256 and exact request/release. Repeated completed requests return the same result. FAILED_STAGED prevents promotion; CORE_UPDATE_FAILED reports host failure; CORE_UPDATED_THEME_REVIEW_REQUIRED preserves actual core success while requiring operator/theme review; COMPLETE requires both health checks. Partial failures are not claimed atomic. No automatic database restore occurs. Use documented compatible code revert only; fresh-database recovery remains separate and maintenance-window authorized.

Qualification must distinguish composition tests with simulated host receipts from actual Nginx/Puma topology checks. No synthetic signature, replay fixture or HTTP rendering result is production signing, live GCS recovery or Chrome accessibility qualification.
