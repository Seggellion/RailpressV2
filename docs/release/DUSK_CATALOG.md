# Bundled Dusk discovery and updates

Core v1 retains the four original GitHub release assets. An optional fifth asset, `dusk-update.json`, publishes a bounded offer. It must match the bytes and SHA-256 for `lib/railpress/dusk-update.json` inside the signed Core inventory. That inventory also carries the vetted signed Dusk directory under `themes/bundled-dusk`. The Core archive is authenticated by the enclosing manifest, keeping digest dependencies acyclic.

To build the native artifact, prepare the verified Dusk directory once and pass the loaded Dusk bundle, minimum Core version and reviewed notes as the builder’s Dusk binding. Include the exact approved installed predecessor tuples and the candidate tuple in the Core compatibility inventory. Publish the returned sidecar bytes unchanged. Securely distribute official signing and trust only through the existing publisher process. The fresh installer validates that `RAILPRESS_INSTALL_THEME` resolves to a trusted package matching the released Dusk binding when present.

Owner-only Themes and Updates show the local installed, active and bundled identities and any verified release offer. The background job reuses existing opt-in, channel, replay protection, cache, lease and transport policy. A manually requested check also uses that worker and a five-minute throttle. A stale or failed check, absent offer, invalid signature or expired manifest does not tell an Owner the installed Dusk is current. The same Core release may still offer Dusk after the operator updates Core.

An older v1 client receives only the Core notification. It can move to a compatible bridge only if all of its validated installed theme tuples and its native environment are admitted. Treat off-list inventory as a compatibility conflict and keep its packages. Expiry and the bounded release list can close an older bridge, requiring an inspected operator path or a separately versioned bridge. Cached metadata does not extend independent UTC execution validity.

Stage via the existing native command with the reviewed Dusk directory. If there is more than one possible inactive Dusk overlay, the operator can supply `--predecessor-overlay ID` for an explicitly reviewed immutable overlay. A same-version digest conflict requires review. Stage does not select a theme or change content. The Owner may preview and explicitly activate or retain the current selection. Keep the previous package/overlay available for the supported revert.
